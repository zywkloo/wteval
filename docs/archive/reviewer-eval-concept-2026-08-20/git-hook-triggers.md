# Git-hook trigger strategy

> **Status:** Superseded as a product direction. Existing tools already cover
> continuous review, re-review, worktrees, cooldowns, and push/PR triggers. Keep
> this only as trigger-policy research; see
> [competitive-landscape-2026-08.md](competitive-landscape-2026-08.md).

Git hooks are useful local triggers, but they are not remote authorization or a
security boundary. They are machine-local, are not cloned automatically, and
can be bypassed. Use them to improve feedback speed; use protected remote checks
for merge authority.

## Recommended trigger split

```text
pre-commit
  -> no wteval model review
  -> optional very fast formatting/static checks only

post-commit
  -> capture the immutable commit
  -> enqueue a non-blocking wteval review
  -> bind the result to HEAD SHA

pre-push
  -> optional fast wtcraft scope/evidence check
  -> reject a known failed or stale required local gate
  -> never wait for a network LLM review by default

GitHub pull_request / synchronize
  -> recompute authorization and verification remotely
  -> run optional advisory reviewer
  -> publish the authoritative/required check result
```

Concrete debounce, cooldown, stale-result, and profile behavior is defined in
[verification-trigger-policy.md](verification-trigger-policy.md).

## Why post-commit is the best local wteval hook

A commit gives wteval a stable subject: parent/base, head SHA, and changed
paths. `post-commit` cannot block commit creation, which is desirable for an
advisory review. The hook should return quickly after queueing or starting a
detached local job:

```bash
wteval capture --repo "$repo" --commit HEAD --enqueue
```

The worker can then run deterministic evidence collection and an optional
reviewer. The result becomes stale as soon as a later commit or amended SHA
supersedes it.

Do not make the hook copy or commit the run bundle. Store it in the configured
local wteval data directory.

## Pre-push policy

`pre-push` can block and is therefore suitable only for fast, predictable local
rules. A useful policy is:

```text
no completed wteval run for pushed SHA -> warn by default
known deterministic gate failure       -> block when strict mode is enabled
advisory reviewer pending/unavailable   -> do not block
```

An explicit strict mode can require a fresh deterministic result, but it still
does not establish protected approval because a developer or agent can bypass
the hook.

## Why remote CI must re-run

Local evidence is useful history, not remote authority. GitHub Actions must
bind its own results to the PR's exact `head_sha`, fetch authorization from the
protected policy ref, and run ordinary CI in the appropriate least-privilege
context. It must not trust a client-supplied `pass` result merely because it was
generated by wteval.

The local and remote runs can share a correlation field such as
`source_commit`, but the remote run receives a new run ID and its own evidence.

## Installation and fallback

A future command may install managed hook stubs explicitly:

```bash
wteval hooks install --post-commit
wteval hooks install --pre-push --mode warn
wteval hooks remove
```

Installation must preserve existing hooks, clearly mark managed blocks, and be
reversible. Manual `wteval review --commit HEAD` and `/finishwt` invocation
remain supported when hooks are absent or disabled.
